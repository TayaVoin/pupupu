## Почему приложение тормозит

### Heatmap пересчитывается каждый кадр

`MapManager::renderMap()` при каждом кадре вызывает `generateHeatmapTexture()`, если включен `showHeatmap`.

Что делает `generateHeatmapTexture()`:

- выделяет `winW * winH * 4` байт;
- фильтрует точки;
- для каждого пикселя окна перебирает все релевантные точки;
- считает haversine distance;
- удаляет старую OpenGL-текстуру;
- создает новую текстуру;
- пишет PNG на диск.

Сложность примерно `O(width * height * points)`. Для окна 600x600 и тысяч точек это миллионы/миллиарды операций в GUI-потоке. Запись PNG каждый кадр дополнительно бьет по диску.

Рекомендация: считать heatmap только при изменении входных данных, zoom, центра, размера окна, радиуса или критерия. Расчет вынести в worker thread, результат кэшировать. PNG сохранять только после завершения нового расчета, не каждый кадр.

### Worker тайлов спит под mutex

В `MapManager::workerThreadFunc()` при пустой очереди поток берет `m_queueMutex` и спит 100 мс, не отпуская lock. В это время GUI-поток не может быстро поставить новые tile requests через `requestTile()`. Это может давать микрофризы и задержки загрузки карты.

Рекомендация: заменить busy sleep на `std::condition_variable` или хотя бы освобождать mutex до sleep.

### Очередь тайлов может забиваться дубликатами

`renderMap()` каждый кадр вызывает `requestTile()` для отсутствующих тайлов. `requestTile()` просто кладет запрос в очередь и не проверяет, что такой тайл уже загружается или уже стоит в очереди. Пока tile не загружен, одинаковый запрос может попасть в очередь много раз.

Рекомендация: вести набор `pendingTiles`/`requestedTiles` и не добавлять дубликаты.

### История копируется каждый кадр

`ServerCore::getHistory()` возвращает копию `std::vector<Measurement>`. `GuiManager::renderSignalPlotsWindow()` и `renderStatisticsWindow()` вызывают это каждый кадр. При `MAX_HISTORY_SIZE = 100000` копирование большой истории станет заметной нагрузкой.

Рекомендация: возвращать snapshot только по необходимости, хранить подготовленные массивы графиков или давать потокобезопасный доступ к агрегированным данным.

### Текстуры тайлов не освобождаются

Текстуры OSM-тайлов создаются лениво при отрисовке и записываются в `tile->texture`, но в деструкторе `MapManager` нет прохода по cache с `glDeleteTextures`. При долгой работе, панорамировании и zoom может расти потребление GPU-памяти.

Рекомендация: удалить GL-текстуры в `MapManager::~MapManager()` или в отдельном методе cleanup, вызываемом из GUI/OpenGL-потока.

### БД загружается синхронно

`loadAggregatedPoints()` делает `SELECT ... ORDER BY timestamp`, затем берет каждую `AGGREGATION_STEP`-ю строку. При большой таблице запрос и сортировка могут тормозить старт, особенно без индексов.

Рекомендации:

- добавить индекс по `timestamp`;
- фильтровать/ограничивать область карты и период;
- агрегировать на стороне SQL;
- не загружать все исторические точки на старте GUI.

## Логические проблемы карты

### Центрирование и координаты считаются линейно

В нескольких местах видимая область карты считается как:

```text
centerLon +/- 180 / 2^zoom
centerLat +/- 90 / 2^zoom
```

Для OSM/Web Mercator это приближение некорректно. Тайлы считаются через Mercator (`latToTileY`, `tileYToLat`), а пиксельные координаты и проверка выхода точки - линейно по градусам. Из-за этого точка может визуально оказываться не в центре окна, особенно по широте.

Рекомендация: все экранные координаты считать через tile-space/world-pixel координаты: lon/lat -> tileX/tileY -> pixel delta от центра.

### `criterion` фактически не работает

GUI предлагает критерии `RSRP`, `RSRQ`, `RSSI`, `Altitude`, но `MapPoint` хранит только одно поле `value`, а БД-загрузка возвращает только `lte_rsrp`. Параметр `criterion` передается в `generateHeatmapTexture()`, но не используется для выбора значения.

Рекомендация: расширить модель `MapPoint` или хранить отдельные слои/значения: rsrp, rsrq, rssi, altitude, earfcn. Для требования "для каждого EARFCN отдельно" добавить EARFCN в БД, DTO, фильтр GUI и ключ кэша heatmap.

### Сохраняется только первая LTE-сота

Если Android присылает несколько сот, `saveToDatabase()` берет только `m.lteCells[0]`. Задание требует графики/легенду по нескольким PCI и heatmap по EARFCN, поэтому текущая схема теряет данные.

Рекомендация: нормализовать схему БД: таблица measurement/session/location и отдельная таблица cell_measurements для каждой соты.

## Проблемы надежности

- В `ServerCore::start()` строка `sock->set(zmq::sockopt::rcvtimeo, 1000);` находится после `return true` и недостижима. Таймаут все равно ставится в `serverLoop()`, но мертвый код надо убрать.
- `parseJson()` глушит все исключения `catch (...) {}` без логирования. Некорректный JSON превращается в пустое измерение.
- `saveToDatabase()` использует фиксированный буфер `deviceIdEsc[256]`; длинный `deviceId` может не поместиться.
- Настройки БД и пароль захардкожены в `include/Config.h`.
- При ошибке БД приложение продолжает работу, но указатель соединения может остаться в неочевидном состоянии.
- `renderMenuBar()` вызывает `exit(0)`, обходя нормальный shutdown объектов.

## Проблемы репозитория
