# Аудит производительности, надежности и проблем

Дата аудита: 2026-06-07.

## Резюме

Сборка `server` проходит. Главный прогресс после аудита от 2026-06-04:
вычисление heatmap вынесено из GUI-потока, добавлена базовая invalidation и
защита от дубликатов tile requests. Старое утверждение "IDW полностью считается
в каждом кадре GUI" больше не актуально.

Тем не менее дорогая часть IDW остается `O(width * height * points)`, публикация
текстуры выполняется каждый кадр, а несколько гонок и блокировок могут приводить
к нестабильности. Ниже проблемы отсортированы по серьезности.

## P0: нарушение данных и основного задания

### Несогласованная схема PostgreSQL

Влияние: исторические точки для heatmap не загружаются на БД, созданной текущим
приложением.

Доказательство:

- `ServerCore::createTable()` не создает `lte_rssi`;
- `saveToDatabase()` не вставляет RSSI;
- `loadAggregatedPoints()` выполняет `SELECT ... lte_rssi ...`.

Рекомендация: добавить совместимую миграцию, колонку в новую схему и INSERT,
проверять SQL NULL через `PQgetisnull()`.

### Потеря нескольких LTE-сот

Влияние: теряются измерения, графики по PCI и корректное разделение heatmap по
EARFCN.

Доказательство: parser заполняет vector, но `saveToDatabase()`, JSON backup,
current GUI, plot-cache и map используют индекс `[0]`.

Рекомендация: хранить measurement/location отдельно от набора cell measurements
и строить временные ряды по PCI.

### Некорректные данные RSSI

Влияние: критерий RSSI показывает RSRP для live-точки и не имеет надежных данных
из PostgreSQL.

Доказательство: в `GuiManager::renderMapWindow()` поле `p.rssi` заполняется из
`lte.rsrp`.

Рекомендация: использовать `lte.rssi`, сохранять RSSI в БД и добавить проверку
контрольным набором данных.

## P0: корректность карты и heatmap

### Смешение Web Mercator и линейных координат

Влияние: центр, точки и тайлы расходятся по широте; pan и zoom не сохраняют
ожидаемую позицию.

Доказательство: номера тайлов считаются функциями Mercator, а экранные
координаты используют `centerLat +/- 90 / 2^zoom` и
`centerLon +/- 180 / 2^zoom`.

Рекомендация: рассчитывать центр, тайлы и точки в единой системе world pixels:
`tileCoordinate * 256`.

### Пустая область IDW окрашивается

Влияние: heatmap визуально сообщает наличие плохого сигнала там, где данных
вообще нет.

Доказательство: при `sumW == 0` значение становится `-140`, но alpha затем
всегда устанавливается в 200.

Рекомендация: оставлять RGBA `(0,0,0,0)`, если в радиусе нет экспериментальной
точки.

### Неполный ключ invalidation

Влияние: изменение данных, EARFCN или значений может оставить старую heatmap.

Доказательство: hash содержит размер vector и координаты только первой точки.
EARFCN filter и `idwPower` не являются явными параметрами ключа.

Рекомендация: использовать version набора данных либо устойчивый hash всех
значимых полей и versioned request/result protocol.

## P1: производительность

### IDW остается вычислительно дорогим

Влияние: worker может долго считать устаревший запрос, нагружать CPU и задерживать
следующий результат.

Доказательство: для каждого пикселя перебираются все relevant points и каждый
раз вычисляется haversine distance.

Сложность:

```text
O(window_width * window_height * relevant_points)
```

Рекомендация:

- считать в уменьшенном разрешении с последующим масштабированием;
- разбить пространство на grid/spatial index;
- предварительно преобразовать точки в локальные метры или world pixels;
- поддержать отмену устаревшего generation id;
- вычислять только после стабилизации pan/zoom либо с debounce.

### Heatmap загружается в GPU каждый кадр

Влияние: повторное копирование CPU -> GPU и возможные микрофризы даже без
изменения данных.

Доказательство: пока `m_heatmapReady == true`, `renderMap()` каждый кадр вызывает
`glTexImage2D`.

Рекомендация: хранить uploaded result version и загружать только новую версию;
при неизменном размере использовать `glTexSubImage2D`.

### Plot-cache перестраивается целиком на каждый пакет

Влияние: при истории до 100000 измерений каждый новый пакет выполняет полный
проход и очистку vector.

Доказательство: `serverLoop()` после каждого receive делает
`clear/reserve/for(m_history)`.

Рекомендация: добавлять новые значения инкрементально в ограниченный ring buffer
по PCI.

### Удаление начала vector истории

Влияние: после достижения лимита каждое новое измерение сдвигает до 100000
элементов.

Доказательство: используется `m_history.erase(m_history.begin())`.

Рекомендация: `std::deque`, circular buffer или индекс начала.

### Синхронная загрузка истории при старте

Влияние: запуск GUI блокируется SELECT, сортировкой и преобразованием до 50000
строк.

Доказательство: `main()` вызывает `loadAggregatedPoints()` до входа в event loop.

Рекомендация: загружать данные асинхронно, ограничивать видимой областью и
выполнять sampling/aggregation в SQL.

## P1: потоки и блокировки

### Ссылка на plot-cache живет без mutex

Влияние: GUI может читать vector одновременно с `clear()` и `push_back()` в
server thread; возможны data race и invalid memory access.

Доказательство: `getCachedRsrpHistory()` берет lock, возвращает `const&`, затем
lock уничтожается.

Рекомендация: возвращать snapshot или immutable `shared_ptr<const PlotData>`.

### История читается без своего mutex

Влияние: модель блокировок не гарантирует согласованность и усложняет дальнейшие
изменения.

Доказательство: после блока с `m_mutex` server thread обходит `m_history` только
под `m_plotMutex`.

Рекомендация: обновлять history и производный cache атомарно по ясному правилу
либо строить cache из локального принятого measurement.

### Tile worker спит под queue mutex

Влияние: GUI не может поставить запрос в очередь до 100 мс.

Доказательство: `sleep_for(100ms)` находится внутри области
`lock_guard(m_queueMutex)`.

Рекомендация: `std::condition_variable` с predicate и уведомлением из
`requestTile()`.

### Tile request после ошибки блокируется навсегда

Влияние: временная сетевая ошибка оставляет пустое место на карте до перезапуска.

Доказательство: ключ удаляется из `m_requestedTiles` только после успешной
загрузки.

Рекомендация: удалять ключ после любого завершения попытки и хранить retry/backoff
отдельно.

### Heatmap worker использует polling

Влияние: постоянные пробуждения каждые 50 мс и задержка реакции.

Доказательство: цикл проверяет atomic flag и вызывает `sleep_for(50ms)`.

Рекомендация: condition variable и generation counter.

## P1: ресурсы

### Повторный `glTexImage2D` и отсутствие cleanup

Влияние: лишняя GPU-нагрузка и утечки/неопределенное поведение при shutdown.

Доказательство: tile textures и heatmap texture не удаляются в контролируемом
GUI cleanup до уничтожения OpenGL context.

Рекомендация: отдельный `shutdownGL()` в GUI-потоке, удаляющий все texture ids.

### Неограниченный memory cache тайлов

Влияние: длительное перемещение и изменение zoom постоянно увеличивает RAM и
GPU memory.

Доказательство: `m_tileCache` не имеет лимита или вытеснения; после upload
сохраняется и RGBA buffer.

Рекомендация: LRU, лимит числа/байтов, освобождение CPU pixels после upload.

### Утечка CURL handle при HTTP 418

Влияние: повторные ответы 418 накапливают ресурсы.

Доказательство: ветка возвращает `false` до `curl_easy_cleanup(curl)`.

Рекомендация: RAII wrapper или единая точка cleanup.

## P2: надежность

- `parseJson()` глушит исключения и сохраняет пустое измерение.
- `ServerCore::start()` не обрабатывает исключения bind/thread creation.
- После `return true` находится недостижимая установка timeout.
- `exit(0)` обходит штатный shutdown.
- Результаты SDL, window, GL context, GLEW и ImGui init не проверяются.
- DB credentials захардкожены.
- `deviceIdEsc[256]` может быть недостаточен.
- Сетевой и DB I/O выполняются последовательно в REP loop, увеличивая latency.
- `clearCache()` не очищает `m_requestedTiles` и не удаляет GL textures.

## P3: мертвый код и предупреждения

Неиспользуемыми или не подключенными к текущему потоку выглядят:

- синхронный `generateHeatmapTexture()`;
- `metersToPixels()`;
- объявленные, но не определенные `drawCircle()` и `getColorForValue()`;
- `GuiManager::requestHeatmapUpdate()` и `generateHeatmap()`;
- `heatmapDirty`, `m_heatmapRequested`, `idwPower`;
- `m_historyVersion`;
- часть history API.

Эти элементы не являются compile blockers, но затрудняют понимание учебного
проекта и скрывают реальное поведение.

## Что исправлено после прошлого аудита

| Старое замечание | Новый статус |
|---|---|
| IDW считается синхронно в GUI каждый кадр | Исправлено: CPU-расчет перенесен в worker |
| Criterion не выбирает данные | Исправлено: switch выбирает четыре поля |
| MapPoint содержит одно value | Исправлено: отдельные rsrp/rsrq/rssi/altitude |
| Нет EARFCN в map model | Исправлено: поле и GUI filter добавлены |
| Tile requests всегда дублируются | Частично исправлено: есть requested set |
| GUI копирует всю Measurement history каждый кадр | Исправлено для текущего графика |
| PNG пишется при каждом GUI-кадре | Исправлено: запись выполняется после worker generation |

## Рекомендуемый порядок

1. Исправить схему БД, сохранение RSSI и multiple-cell data flow.
2. Исправить IDW и перевести карту на world-pixel Web Mercator.
3. Устранить data races и переделать workers на condition variables.
4. Публиковать heatmap texture только по новой версии.
5. Добавить bounded history и tile caches.
6. Усилить обработку ошибок и штатный shutdown.
7. Удалить мертвый код и warnings.

Детальные задачи, примеры и критерии готовности находятся в
`ssot/remediation-plan.md`.
