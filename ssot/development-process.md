# Процесс разработки и проверки

Дата: 2026-06-07.

## Роли окружений

В проекте есть два разных контура работы.

Первый контур - `dev environment`: этот MacBook с Codex. Здесь мы читаем код, делаем правки, ведем SSOT-документацию, проверяем CMake-конфигурацию и ищем ошибки компиляции. Этот компьютер не является целевой машиной для полноценного запуска приложения.

Второй контур - `stage environment`: Windows/WSL-компьютер студентки. Там выполняется реальный запуск и дебаг приложения, потому что сервер должен быть в одной сети с Android-телефоном, который отправляет данные по ZMQ. Проверка приема данных, карты, тайлов, PostgreSQL и поведения GUI должна происходить там.

## Что делать на dev environment

Техническое описание dev environment хранится в `ssot/env/dev.md`.

- Редактировать `src/`, `include/`, `CMakeLists.txt`, `README.md`, `AGENTS.md` и `ssot/`.
- Использовать `cmake` для статической проверки конфигурации и поиска ошибок сборки.
- Запускать CMake/build-проверки во временной директории вне репозитория.
- Не создавать и не коммитить локальные `build/`, `build_wsl/`, `tile_cache/`, `measurements.json`, `imgui.ini`.

## Что делать на stage environment

Техническое описание stage environment хранится в `ssot/env/stage.md`.

- Собирать и запускать приложение в целевой среде.
- Подключать Android-устройство в той же сети.
- Проверять фактический ZMQ-прием данных, PostgreSQL-запись, отображение текущей точки, OpenStreetMap-карту и тепловую карту.
- Если компьютер студентки работает под Windows/WSL, локальная папка `build_wsl/` может использоваться только там как локальный артефакт сборки. В git ее возвращать нельзя.

## Почему `build/` и `build_wsl/` не храним в git

`build/` и `build_wsl/` - это не исходники. В них лежат CMake cache, object files, static libraries, бинарники, runtime-логи, `imgui.ini`, `measurements.json` и кэш OSM-тайлов.

Эти данные зависят от конкретной машины и среды. На dev environment они не нужны для бизнес-процесса разработки, а на stage environment должны пересоздаваться локально.

## Статус окружений

Актуальный статус dev и stage окружений фиксируется только в `ssot/env/dev.md` и `ssot/env/stage.md`.

## Обязательный порядок проверки

Изменения проверяются в два последовательных этапа.

### 1. Dev compile-check

На MacBook выполняется чистая CMake/Release-сборка во временной директории вне
репозитория. Этот этап проверяет:

- поиск зависимостей;
- компиляцию всех translation units;
- линковку target `server`;
- новые warnings и ошибки.

Успешный результат должен заканчиваться строкой:

```text
[100%] Built target server
```

### 2. Stage runtime-check

Только после успешной dev-сборки изменения переносятся на stage/WSL. Там
проверяются реальные сценарии:

- прием валидного и невалидного JSON от Android;
- ответ ZMQ;
- запись и чтение PostgreSQL;
- несколько LTE-сот и линии PCI;
- загрузка и кэш OSM;
- центрирование, pan и zoom;
- четыре критерия IDW и EARFCN;
- сохранение heatmap PNG;
- закрытие приложения без зависания.

Compile-check не считается заменой runtime-check. Если stage-проверка не
выполнялась, это явно отмечается в аудите или отчете.
